# 06 多校隔离实现说明

## 1. 目标
任何一次读写，都不能拿到非本校数据；平台侧角色（客服/平台管理员）跨校访问必须**显式授权 + 留痕**。

## 2. 三级防护

### 2.1 中间件层：`middleware/school-scope.js`
```js
// 伪代码（实现见源码）
export function schoolScope(req, res, next) {
  // 1) 学生：学校来自登录态，客户端传什么都无效
  if (req.user && CROSS_SCHOOL_ROLES.includes(req.user.role) === false) {
    req.schoolId = req.user.schoolId;
    if (!req.schoolId) throw new AppError(ERR.SCHOOL_REQUIRED);
    return next();
  }
  // 2) 客服 / 平台管理员：必须显式传 schoolId，并校验权限与记录审计
  const sid = Number(req.query.schoolId || req.body.schoolId || req.params.schoolId);
  if (!sid) throw new AppError(ERR.SCHOOL_REQUIRED, '跨校角色必须显式指定 schoolId');
  req.schoolId = sid;
  auditService.record({ actorId: req.user.id, action: 'cross_school_access', targetType: 'school', targetId: sid, ip: req.ip });
  next();
}
```
要点：
- **学生端永不接受客户端传入的 `schoolId`**（防止改包越权），一律取自 JWT。
- 跨校角色访问必须显式传 `schoolId`，并写 `audit_logs`。
- 中间件挂在所有业务路由前，`/auth`、`/schools`（公开查询）除外。

### 2.2 数据访问层：repository 强制 schoolId
```js
// 所有 repository 方法签名都要求 schoolId，缺失直接抛错
export async function findBookById(conn, schoolId, id) {
  assertSchoolId(schoolId);
  const [rows] = await conn.query(
    'SELECT * FROM books WHERE id = ? AND school_id = ? AND deleted_at IS NULL',
    [id, schoolId],
  );
  return rows[0] ?? null;
}
```
- SQL 中 `school_id = ?` 是**强制条件**，且 `school_id` 与主键同为第一优先级索引。
- 跨模块引用对象（如订单里的 `book_id`）在 service 层再做一次 `assertSameSchool(book, req.schoolId)` 校验（双保险）。
- 平台级共享数据（词库、知识库、配置）使用 `school_id IS NULL OR school_id = ?` 的显式例外，并在代码中集中封装为 `scopeSql()`，避免散落各处。

### 2.3 数据库层
- 联合唯一键把学校维度写进约束：`users(school_id, student_no)`、`banned_words(word, scope, school_id)`、`configs(scope, school_id, config_key)`。
- 复合索引 `(school_id, status, created_at)` 让本校列表查询都在索引内完成。

## 3. 跨校专区
- 开关：`schools.cross_school_enabled` + `schools.cross_school_mode`（`off` 关闭 / `mail` 仅邮寄）。
- 开启后，图书列表增加「跨校」筛选：查询条件变为 `(school_id = ? OR (cross_school = 1))`，跨校订单仅允许邮寄方式发货。
- 默认关闭：种子数据中 3 所学校只有 1 所开启，用于验证默认不越权。

## 4. 越权拦截的验证方式
`server/tests/integration/isolation.test.js`：
1. A 校学生读取 B 校图书详情 → 期望 `404`（不是 403，避免泄露存在性）。
2. A 校学生携带 `?schoolId=B` 请求列表 → 期望仍返回 A 校数据（参数被忽略）。
3. A 校学生用 B 校图书 ID 下单 → 期望 `BOOK_NOT_FOUND`。
4. 校管只能看到本校举报与认证队列。
5. 客服不传 `schoolId` → 期望 `SCHOOL_REQUIRED`。

## 5. 常见坑与规避
- **写操作也要过滤**：`UPDATE books SET ... WHERE id = ? AND school_id = ?`，并用 `affectedRows` 判断是否命中，避免“读到本校、改到别校”。
- **关联查询**：JOIN 时两侧都带 `school_id` 条件，防止通过 `book_id` 反查跨校用户。
- **缓存 key 必须带 schoolId**：`cfg:{schoolId}:{key}`、`book:detail:{schoolId}:{id}`，避免缓存穿透越权。
- **导出/统计接口**：平台管理员跨校统计走单独的 `admin` 路由与专用 SQL，不复用学生端 repository。
